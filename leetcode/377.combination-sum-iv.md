# [377. Combination Sum IV](https://leetcode.com/problems/combination-sum-iv/description/)

> The problem is misleading, it actually asks for "permutations" instead of "combinations". The order of the numbers matters, so `(1, 2)` and `(2, 1)` are different.

## Key Insights
* It counts the number of permutations that can combine to `target`, so `(2, 1, 1)` and `(1, 2, 1)` are different.
* Suppose target is `4`, and `nums = [1, 2, 3]`, the last step we took to reach `4` had to be adding `1`, `2`, or `3`. If the last step was adding `1`, then we must have previously eached target `3`, and so on. Therefore, the total ways to reach `4` is simply the (Ways to reach `3`) + (Ways to reach `2`) + (Ways to reach `1`).
* It's a classic counting problem: "count the number of ways to do something", a huge hint for **DP**. For the `target`, we can break it down into sub-problems: the number of combinations of `target - nums[i]`. And the combination is `1` when we reach `0` from `target - nums[i]`. (Similar to [518. Coin Change II](../leetcode/518.coin-change-ii.md), but order does not matter, counting the number of permutations, `(2, 1, 1)` and `(1, 2, 1)` are the same)

### Abstraction
Let `dp[t]` = the number of valid permutations that sum to `t`. Then the state transition is:
```js
dp[t] = sum(dp[t - nums[i]]) for all i where nums[i] <= t
```

```js
nums = [1, 2], target = 3

                 [3]
               /     \
            -1/       \-2
             /         \
           [2]         [1]
          /   \        /  \
        -1     -2    -1    -2
       /         \   /       \
     [1]         [0] [0]     [-1]
    /   \         ^   ^       ^
  -1     -2      (Valid)    (Invalid)
  /       \
[0]       [-1]
 ^         ^
(Valid)   (Invalid)

// Top-Down Recursive
f(3) =
    1 + f(2)
    2 + f(1)
f(2) =
    1 + f(1)
    2 + f(0)
f(1) =
    1 + f(0)
    2 + f(-1)

f(0) = 1
f(-1) = 0 // Or we can skip the negative cases

// Backtracking
f(1) = 1 + 0 = 1
f(2) = 1 + 1 = 2
f(3) = 2 + 1 = 3
```

> Why Greedy failed? Greedy attempts to make the local best choice, such as always taking the largest number to reach the target quickly. However, it's finding **a single optimal path** (like the fewest number of steps to reach the target), but the problem asks for **counting all possible paths** (the number of ways to reach the target). Greedy will miss many valid paths, so it fails.

## Top-Down DP
```kotlin
fun combinationSum4(nums: IntArray, target: Int): Int {
    val memo = HashMap<Int, Int>()
    return topDown(nums, target, memo)
}

private fun topDown(nums: IntArray, target: Int, memo: HashMap<Int, Int>): Int {
    // Base cases
    if (target == 0) return 1
    if (target < 0) return 0
    if (target !in memo) {
        var combinations = 0
        for (num in nums) {
            combinations += topDown(nums, target - num, memo)
        }
        memo[target] = combinations
    }
    return memo[target]!!
}

// Or equivalently, we check if num <= target, if so, we can add it to the combinations
private fun topDown(nums: IntArray, target: Int, memo: HashMap<Int, Int>): Int {
    if (target == 0) {
        return 1
    }
    // Here we don't check if target < 0, because we check num <= target in the for loop
    if (target !in memo) {
        var count = 0
        for (num in nums) {
            // We only add it to the combinations if num <= target
            if (num <= target) {
                count += sum(nums, target - num, memo)
            }
        }
        memo[target] = count
    }
    return memo[target]!!
}
```

### Complexity Analysis
- Top-Down Recursion:
    - **Time Complexity:**: Each `topDown(target)` call will split into `n` subproblems, the maximum depth of the recursion tree is `target` (in the worst case, we have `nums[i] == 1` and we always subtract `1`), so the total number of calls is `O(n^target)`.
    - **Space Complexity:** `O(target)` for the recursion stack and memoization table.
```js
                                 topDown(target)
             /                        |                        \
       - nums[0]                    - nums[1]                - nums[2]
          /                           |                           \
topDown(target - nums[0])   topDown(target - nums[1])   topDown(target - nums[2])
  /      |      \              /      |      \             /      |      \
...     ...     ...                   │                           │
```

- Top-Down DP: 
    - **Time Complexity:**: Each `topDown(target)` call will iterate through `n` numbers, and we have `target` unique subproblems, so total is `O(n * target)`. 
    - **Space Complexity:** `O(target)` for the memoization table.

> 正確推導：
>
> 1. 狀態總數：target 從 $1$ 變化到 $T$，總共有 $T$ 種可能。
> 2. 內部工作量：仔細看 `if (memo[target] == null)` 裡面的邏輯，這裡有一個 `for (i in nums.indices)` 的迴圈。這代表每次計算一個全新的狀態時，程式必須跑一個大小為 $N$ 的迴圈。
> 3. 相乘結果：$T \times O(N) = O(T \times N)$。

## Bottom-Up DP
Let `dp[i]` = the number of ways to sum to `i`. We can build up results for each target sum from `1` to `target`, so we iterate each target sum, then for each target sum, we iterate each num in `nums` as nested loop.

> This order matters, it's used to count permutations, not just combinations.

To make sum `i`, try putting each `num` to the end of the combination, and see how many ways there are to from `i - num`.


```kotlin
fun combinationSum4(nums: IntArray, target: Int): Int {
    return bottomUp(nums, target)
}

private fun bottomUp(nums: IntArray, target: Int): Int {
    val dp = IntArray(target + 1)
    dp[0] = 1 // Base case: target == 0, we have 1 way to form it: use nothing
    for (i in 1..target) {
        for (num in nums) {
            if (num <= i) {
                dp[i] += dp[i - num]
            }
        }
    }
    return dp[target]
}
```

- **Time Complexity**: `O(target * n)`, where `n` is the length of `nums`.
- **Space Complexity**: `O(target)`.
